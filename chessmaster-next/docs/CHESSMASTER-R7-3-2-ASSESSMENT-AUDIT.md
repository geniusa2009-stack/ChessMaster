## Server-authoritative selection
- `selectAttemptItems` (pure, deterministic given its RNG) issues 2 DISTINCT contexts per mandatory competency, preferring contexts NOT in the learner's most recent attempt (rotation). It contains no answers.
- `POST /api/foundations/start` (POST only — issuing an attempt is a stateful, server-bound action) runs selection with a cryptographically secure RNG (node:crypto `randomInt`, never `Math.random`) and returns client-safe prompts only.

## Attempt token (binds issued items to the attempt)
- `foundations.token.server.ts` (`import "server-only"`) signs an HMAC-SHA256 token carrying { attemptId, userId, issuedItemIds, iat, exp } — NO answer keys. Key derived from `SUPABASE_SERVICE_ROLE_KEY` (server-only).
- Verification is constant-time, checks expiry, and binds the token to the authenticated user; a tampered signature, forged payload, wrong key, or expired token is rejected.

## Submission integrity & idempotency
- `POST /api/foundations/attempt` verifies the token, rejects any answer id the server did not issue, and grades ONLY the issued items (`gradeFoundation(answers, issuedIds)`), so evidence can never come from another attempt or an un-issued bank item.
- Evidence is recorded idempotently via `upsert(..., { onConflict: "user_id,attempt_id", ignoreDuplicates: true })` backed by migration 0016's unique index. A replayed or concurrent duplicate of the same attempt returns the STORED result and never duplicates evidence or changes the outcome.
- `foundation_assessment` pass latch unchanged: a prior pass is never downgraded; kept score = max.
